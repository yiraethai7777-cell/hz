# 보이스룸 네트워크 캡처 비교 (2026-11-11)

> 원본 PCAPNG 파일은 개인정보·세션 메타데이터를 포함할 수 있어 저장소에 업로드하지 않습니다.
> 이 문서는 사용자 제공 `baseline.pcapng`, `create.pcapng`, `create-test.pcapng`에서 확인한 집계치만 기록합니다.

## 개요

| 파일 | 패킷 수 | 관측 시간 (UTC) | TCP/995 관련 | IPv6 UDP | 원본 바이트 대비 저장 비율 |
|---|---:|---|---:|---:|---:|
| `baseline.pcapng` | 127 | 2026-11-08 16:35:12~16:35:22 | 0 | 1 | 32.25% |
| `create.pcapng` | 116 | 2026-11-08 16:31:15~16:31:45 | 5 | 7 | 31.09% |
| `create-test.pcapng` | 311 | 2026-11-08 16:35:43~16:35:53 | 36 | 95 | 31.35% |

주의: 파일 이름과 달리 `create` 캡처는 `baseline`보다 시간상 약 4분 먼저 기록됐습니다. 따라서 각 파일의 라벨은 실험자가 붙인 단계명이지 엄밀한 연속 A/B 캡처 증거는 아닙니다.

## 확인된 프로토콜 흔적

1. `create.pcapng`: 클라이언트 → TCP/995에서 TLS ClientHello로 보이는 `16 03 01` 레코드 시작이 관찰됩니다. 이 캡처 내 해당 포트 패킷은 5개이고, 저장된 TCP 페이로드 합계는 56바이트로 **성공한 TLS 세션 전체를 포함하지 않습니다**.
2. `create-test.pcapng`: TCP/995에서 `16 03 03`, `17 03 03` TLS 핸드셰이크/애플리케이션 레코드 흔적이 관찰됩니다. TLS 암호화되어 있기 때문에 이 캡처만으로 실제 보이스룸 생성 명령이나 BSON 본문을 복구할 수 없습니다.
3. `create-test.pcapng`: UDP 페이로드에서 STUN magic cookie `21 12 A4 42`를 가진 패킷, DTLS 헤더로 보이는 `16 FE FF`, RTP v2 양식 `90 6F` 패킷 46개, RTCP 수신 보고서 양식 `81 C9` 패킷 5개를 관찰했습니다. **실시간 음성 연결 관련 통신과 일치**하지만, 이 패킷만으로 보이스룸 개설 요청의 스키마를 단정할 수는 없습니다.
4. 캡처가 패킷당 약 128바이트로 잘린 사례가 많습니다. 각 파일의 원본 바이트 대비 저장 비율은 약 31~32%이므로 후속 확인에서는 전체 패킷 길이를 보존하는 캡처가 필요합니다.

## 설계에 반영할 결론

- 생성 명령의 실제 VOX 명령 코드, 메시지 직렬화, 인증, 응답 검증 형식은 **아직 미확인**입니다. `shared/voice-room-direct-protocol.js`의 `wire.makeVoiceRoom`은 검증된 구현체가 제공될 때만 호출합니다.
- TCP/995 흐름과 UDP STUN/DTLS/RTP/RTCP 연결 흐름은 상이한 단계일 수 있습니다. 표준 STUN/DTLS/RTP 구현만으로 카카오톡 서버의 보이스룸 생성 명령이 구현되는 것은 아닙니다.
- Windows 데스크톱 카카오톡 캡처로는 Android Noa의 `makeVoiceroom` API가 보낸 명령을 입증할 수 없습니다. 지금 작동 중인 Noa 경로와 연결 지어 해석하려면 **동일 기기·동일 시간대의 성공 캡처**가 필요합니다.
- 이번 결과는 직통 생성 성공을 증명하지 않습니다. 기존 Noa 어댑터, 운영 로그인, Railway 서비스에는 변경하지 않습니다.

## 다음 검증에 필요한 근거

- 성공·실패 순간이 각각 기록된 완전한 패킷 길이의 캡처 및 이벤트 시각
- 사용자 본인 계정으로 실행한 동일 환경에서의 생성 요청/응답 구분
- 실제 서버 응답에 기반한 room ID 및 활성 상태 확인
- 계정 1개가 두 방의 동시 진행자 세션을 유지할 수 있는지에 대한 별도 실험
