# NEXI 보이스룸 명령어 및 실제 서버 연동

## 명령어

현재 운영 방식은 Railway 단독 VOX 생성입니다. 생성은 성공하지만 약 30초에 서버 종료 신호 `11009` / `reason=1002`를 수신하는 문제가 남아 있습니다. Android, Iris, Noa 브리지는 사용하지 않습니다.

- `#보룸시작 [제목]` / `#보룸켜기 [제목]` (`#보이스룸시작`, `#보이스룸켜기`): 생성 요청 (최대 40자)
- `#보룸상태` / `#보이스룸상태`: 실제 서버 상태 및 봇 권한 조회
- `#보룸종료` / `#보룸끄기` (`#보이스룸종료`, `#보이스룸끄기`): 실제 서버에서 개설 상태가 확인된 경우에만 종료 요청
- `#보룸명령어` / `#보이스룸명령어`: 기능 안내

기존 `!` 접두사 및 접두사 없는 명령어도 라우터에서 받아들입니다. 사진처럼 `#보룸시작.` 또는 `#보룸시작 .`도 인식하며 이 경우 기본 제목은 '보이스룸'입니다. 방별 접두사 정책과 전체 봇 ON/OFF가 우선합니다.

## 보이스룸 수신 신호 진단 (1차, 2026-11-08)

카카오톡에서 **직접 보룸을 만든 다음**, NEXI가 해당 방의 관련 서버 이벤트를 수신하는지 시험하는 기능입니다.

- `#보룸감지시작`: 해당 방에서 3분간 이벤트 메타데이터 감시 시작
- `#보룸감지`: 수신한 **후보**의 종류·건수 표시 (메시지 본문/닉네임/인증 정보 저장하지 않음)
- `#보룸감지종료`: 감시 중단
- 방장·부방장 또는 봇 계정만 사용. 기존 봇 ON/OFF·방별 명령어 제한이 먼저 적용됩니다.

검증 순서:

1. 봇이 참여한 오픈채팅방에 가서 `#보룸감지시작` 입력.
2. 카카오톡 앱의 + 버튼으로 **그 방에서 직접** 보이스룸 개설.
3. 3분 이내 `#보룸감지` 입력해 관련 신호가 잡혔는지 확인.
4. 보룸을 종료한 뒤 필요하면 새 관찰을 시작하고 종료 이벤트 수신 여부 비교.

아직 실제 활성 상태를 확인하는 공개 서버 API나 전용 VOX 수신 프로토콜이 없습니다. 진단 도구는 기존 메시지의 **유형 51/52**(역사적인 VOIP/LIVETALK 형식) 및 보이스룸 관련 이름의 LOCO 푸시가 나타나는지만 살펴봅니다. 이 메타데이터는 **현재 오픈채팅 보이스룸에 해당한다고 검증되지 않았으며**, 후보가 잡혀도 **'열림' 판정을 하지 않습니다**. 후보가 없다고 해서 비활성 상태인 것도 아닙니다.

운영 서버에서 **새 패킷을 송신하거나, 방 정보/메시지 본문/토큰을 로그로 남기지 않습니다**. 기존 NEXI 일반 기능에는 영향을 주지 않도록 독립적인 이벤트 리스너로 연결합니다. 3분이 지나면 기록은 만료됩니다.

### 개설·종료 표시의 후보 구분 (2차 시험)

2026-11-08 실제 오픈채팅 시험에서 `#보룸감지`가 개설 직후 **유형 52 1건**, 종료 직후 **유형 52 누적 2건**을 표시한 사례가 있었습니다. 이것은 실제 활성 상태 API가 아니라 수신 채팅 유형의 관찰 결과입니다.

- 수신 유형 52의 메시지 표시가 정확히 `보이스룸`이면 **개설 표시 후보**로 분류합니다.
- 표시가 `0:16` 같은 시간 형식이면 **종료 표시 후보**로 분류합니다.
- 첨부 데이터가 있으면 최대 12개의 안전하게 정제한 **필드명과 자료형만** 표시합니다. 값, 본문, 사람 이름, 사용자 ID, 인증 정보, URL 등은 출력하지 않습니다.
- 보름 메시지가 다른 방식으로 표시되거나 값이 별도 필드에 들어 있다면 해당 후보 표시가 나오지 않을 수 있습니다.
- 이러한 단서는 **추정이며 실제 보이스룸이 열렸거나 종료됐다는 서버 검증이 아닙니다**. `#보룸상태`가 활성 상태로 바뀌지 않습니다.

추가 확인: 같은 방에서 `#보룸감지시작` → 직접 개설 → `#보룸감지` → 직접 종료 → `#보룸감지`. 두 번째 결과에 서로 다른 표시 후보나 첨부 필드 구조가 나오는지 비교하세요. 

### 유형 52 첨부 데이터로 개설·종료 구분 (3차 시험)

실제 NEXI에서 개설 직후, 종료 직후 각각 **유형 52 1건씩**, 동일한 첨부 필드 `csIP:string,csIP6:string,csPort:number,duration:number,type:string`이 관찰되었습니다.

공개된 제3자 Android 보이스룸 분석 자료에는 유형 52 메시지 첨부의 `type`이 `vr_invite`(개설·초대) 또는 `vr_bye`(종료)라는 정보가 있습니다. 이를 **개설 이벤트 후보 / 종료 이벤트 후보**로만 분류합니다.

- `#보룸감지`를 실행하면 `type=vr_invite` / `type=vr_bye` 및 0~172800 사이의 정수 `duration`(초)만 표시합니다.
- `csIP`, `csIP6`, `csPort`, `callId`, 인증값 등은 값 자체를 **수집·출력하지 않습니다**. 다른 유형 문자열도 출력하지 않습니다.
- 수신 이벤트는 실제 보룸의 **현재 활성 상태 조회가 아닙니다**. 단순히 시작 메시지가 왔다는 이유로 `#보룸상태`를 활성으로 판정하지 않습니다.
- 이번 연구에서는 추가 소켓 연결, 패킷 전송, 음성룸 생성 요청을 하지 않습니다.

출처(공식 자료가 아닌 외부 구현·분석):
- [Android 25.8.1 유형 52 수신 파서](https://github.com/Lukim99/node-kakao-stable/blob/4d251bf35dccfdc8c241070449907e7eab1aac8b/v5/packages/protocol-android/src/voice-room.ts)
- [Vox30 VoiceRoom 분석 자료](https://github.com/itznullbyte/itznullbyte.github.io/blob/d0fe05d60315ca450cc84595f9ce2593d3266611/src/content/posts/vox_room/index.md)

검증 방법: `#보룸감지시작` → 앱에서 보룸 직접 개설 → `#보룸감지` → 보룸 종료 → `#보룸감지`. 두 결과에 `vr_invite`와 `vr_bye`가 각각 표시되는지 확인합니다.

### 관리 ON 방 자동 감지

`!관리on`으로 관리 기능을 켠 오픈채팅방에서는 보이스룸을 직접 개설하거나 종료할 때 **`#보룸감지시작` 없이** 자동으로 감지합니다.

- 카카오톡 수신 채팅 유형 52의 첨부 `type=vr_invite` → **🎙️ 보이스룸 개설 감지** 안내.
- `type=vr_bye` → **🎙️ 보이스룸 종료 감지** 안내. 유효한 `duration`이 있으면 진행 시간 표시.
- `!관리off`가 설정된 방은 자동 알림을 보내지 않습니다.
- `!봇끄기`로 봇이 OFF인 방도 자동 알림을 보내지 않습니다.
- 방 ID와 카카오톡 로그 ID로 중복 수신을 걸러내며, 다른 방은 서로 독립적으로 동작합니다.
- `#보룸상태`와 `#보룸감지`는 마지막 자동 수신 이벤트를 볼 수 있습니다.
- 기존 3분 수동 진단 기능은 별도로 유지됩니다.

**제한:** 서버 현재 활성 상태를 직접 조회하는 기능이 아닙니다. NEXI 재시작 시 마지막 자동 감지 기록은 초기화되고, 연결이 끊긴 동안 발생한 이벤트나 오래된 동기화 메시지는 자동 안내하지 않을 수 있습니다. IP·통화 세션 ID·인증키·메시지 본문 등은 저장하거나 출력하지 않습니다.

## 현재 개발 단계 (2026-11-08)

**중요:** 현재 저장소에는 카카오톡의 보이스룸을 실제 생성/종료하는 검증된 프로토콜 구현이 없습니다. `shared/voice-room.js`는 명령어 라우팅, 권한 검증, 상태 확인, 동시 요청 제어를 제공하는 컨트롤러입니다.

- 현재 상태에서 `#보룸켜기`는 실제 생성 요청을 보내지 않고 API 미연동을 안내합니다.
- `#보룸끄기`도 실제 종료 API와 상태 조회 API가 모두 연결되기 전에는 요청하지 않습니다.
- 임의의 LOCO 메서드, BSON 필드 또는 VOIP 암호화 값을 추정해 실제 카카오톡 서버로 송신하지 않습니다.
- Railway에서 별도 기기 없이 실제 보룸을 개설하려면 검증된 서버 측 생성·상태·종료 프로토콜 구현이 필요합니다.

공식 Kakao Developers REST API에는 카카오톡 오픈채팅 보이스룸 생성/종료 API가 없습니다.
구형 VOIP 메모의 `0x272c`(create live talk)는 현재 오픈채팅 보이스룸 기능과 동등한지 확인되지 않았고 일반 LOCO 메서드가 아닙니다.

## 검증된 어댑터의 연결 계약

동작 검증이 끝난 서버 프로토콜 구현을 준비한 경우에만 런타임 `client.voiceRoomAdapter`에 연결합니다.

```js
client.voiceRoomAdapter = {
  async create({roomId, title, openLinkId}) {
    // 실제 생성 응답/상태 조회로 검증된 경우에만 반환
    return {created: true, verified: true, status: 0, voiceRoomId: 'SERVER_ID'};
  },
  async status({roomId}) {
    // 조회 결과가 해당 채팅방의 활성 상태임을 서버 응답으로 확인할 것
    return {active: true, verified: true, roomId, voiceRoomId: 'SERVER_ID'};
  },
  async stop({roomId, voiceRoomId}) {
    // 검증된 실제 종료 응답인 경우에만 반환
    return {closed: true, verified: true, status: 0, roomId};
  }
};
```

위 객체는 **메서드의 형식만 설명하는 예시**로, 실제 카카오톡 API를 구현하는 실행 코드는 아닙니다. 서버 검증 없이 `verified: true`를 반환하면 안 됩니다.

안전 조건:
1. 일반 실행자는 해당 오픈채팅방의 방장(1) 또는 부방장(4)이어야 합니다. 동일한 카카오 계정 ID로 확인된 봇 계정은 이 명령어 권한 검사를 통과합니다. 실제 서버 생성·종료 성공은 카카오톡 서버 권한/API 응답에 따릅니다.
2. 생성 요청은 `created: true, verified: true` 또는 서버 조회의 `active: true, verified: true`를 확인한 뒤에만 성공 안내
3. 종료 요청 직전에 해당 방의 활성 상태를 확인하고, 종료 응답 `closed: true, verified: true, roomId` 또는 상태 조회의 `active: false, verified: true, roomId`로 종료 검증
4. 생성·종료 요청은 동일 방에서 동시 실행 차단
5. 상태 불명, 응답 오류, 인증/권한 오류 시 추정 성공 메시지 금지

## Railway 서버형 VOX 참가 전제: 수신 초대의 접속 정보 추출 (2026-11-09)

**참고(기존 분석 자료):** Android 앱은 채팅 유형 52의 최신 `vr_invite` 첨부에서 `callId`, `csIP`, `csIP6`, `csPort`를 가져와 로그인된 Android 카카오톡의 `joinVoiceroom()` 메서드에 전달합니다. VOX 인증·세션 협상·오디오 연결은 카카오톡 앱이 수행하므로 서버형 Node.js 클라이언트는 해당 부분을 별도로 구현해야 합니다.

### 구현

- `shared/voice-room-join-info.js`: 기존 `voice-room-observer.js`의 attachment parser를 재사용해 이미 수신한 `vr_invite`에서 정확한 정수 ID, 올바른 IP, 1~65535 범위의 포트만 허용합니다.
- `vr_bye`를 받으면 접속 정보를 즉시 폐기하고, 이전 로그 ID의 중복/재동기화 초대가 다시 활성으로 보이지 않도록 차단합니다.
- 접속 정보는 **메모리에서만 최대 5분** 유지하며 SQLite·PostgreSQL·디스크 파일·채팅 메시지·로그에는 저장하지 않습니다. 최대 128개 방만 유지합니다.
- `#보룸참가상태` 및 `#보룸참가`에서는 수신 준비 여부만 알립니다. **통화 ID·VOX 서버 IP/포트는 출력하지 않습니다.**
- `hz-new.js`에 별도 수신 리스너를 추가했습니다. 기존 Railway QR 인증·KakaoForge 연결·명령어 접두사·보이스룸 알림 로직은 유지합니다.
- Railway 직접 VOX 연결이 없더라도 명령어는 인식합니다. 접속 정보를 받았어도 **독립적인 VOX 암호화/인증 클라이언트가 없으므로 참가하지 못했다고 분명히 안내합니다.**

### 다음으로 반드시 구현·검증할 단계

1. 앱의 **현재 버전**에서 사용되는 VOX 참가 요청의 정확한 인증 절차·바이트 규격·암호화 및 서버 응답 확인
2. NEXI의 기존 로그인 세션을 끊지 않고 VOX에 적법하게 인증하는 방법
3. VOX 참가 후 유지할 heartbeat, media/ICE/WebRTC 연결 및 정상 퇴장 처리
4. 실제 참가자 목록에서 NEXI 계정이 나타나는 라이브 시험

2020년 VOIP 메모에 있는 TLS/SEED 기반 구형 제어 패킷은 **2026년 보이스룸 참가와 동일하다고 검증되지 않았으므로 임의로 송신하지 않습니다.** 제공된 DLL의 복호화 함수만으로 가입 인증이 가능하다고 판단하지 않습니다.

테스트: `node --test test/voice-room-join-info.test.js`. 테스트는 실제 네트워크나 VOX 세션에 접속하지 않고 이미 알려진 이벤트 구조를 모의합니다.

## Railway 직접 VOX 참가·역할 관찰 1차 구현 (2026-11-13)

명령 `!보룸참여` 및 `!보룸참여상태`는 기존 보룸 참가 명령에 연결했습니다.
기존 직접 VOX 생성(`!보룸시작`, `#보룸시작`)과 로그인 흐름은 변경하지 않았습니다.
`shared/vox30-role-state.js`는 VOX 서버의 12011 멤버 명단에서 봇 계정이 속한
`moderators`/`speakers`/`listeners` 목록만 판독합니다. 서버가 명시적으로 봇을
단 한 그룹에 포함한 경우에만 `진행자`/`스피커`/`리스너`를 표시합니다.
원시 패킷·타인 ID·VOX 서버 주소 및 OAuth 토큰은 저장하거나 출력하지 않습니다.

**현재 제한사항:** 초대 첨부에서 세션 위치와 callId를 가져오는 기능은 기존에 존재하지만,
서버 참가용 11002(LOGIN) 요청의 정확한 인증 BSON 스키마와
12023(CLIENT_OFFER)의 동작·역할 수락 응답 패킷은 검증되지 않았습니다.
따라서 `!보룸참여`는 현재 무리하게 참가 패킷을 전송하지 않고 부족한 절차를 안내하며,
진행자·스피커 초대에 자동 응답하지 않습니다. **실제 참가와 권한 수락은 미구현**입니다.

검증: `node --test test/vox30-role-state.test.js test/voice-room.test.js test/voice-router.test.js test/voice-room-permission.test.js`
